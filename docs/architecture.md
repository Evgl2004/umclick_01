# Архитектура umclick

umclick - MVP платформы интерактивных викторин в стиле Kahoot. Архитектура пока монолитная по репозиторию, но разделена на независимые слои: backend API, Flutter Web frontend, инфраструктура Docker Compose и локальные quality-gate скрипты.

## Цели архитектуры

- Быстро развивать MVP без микросервисной сложности раньше времени.
- Держать игровой live-flow проверяемым тестами.
- Не смешивать UI, API-клиент, domain helpers и инфраструктурный код.
- Явно версионировать обработку персональных данных и согласий.
- Поддерживать возможность будущего выделения частей в отдельные сервисы.

## Верхнеуровневая схема

```text
Teacher Browser / Participant Browser
               |
               v
        Flutter Web frontend
               |
       HTTP REST + WebSocket
               |
               v
 Django + DRF + Channels backend
       |              |
       v              v
   PostgreSQL       Redis
                      |
                      v
              Celery worker/beat
```

## Основные компоненты

| Компонент | Путь | Ответственность |
| --- | --- | --- |
| Backend | `backend/` | REST API, WebSocket, общие квоты, машина проведения, финализация, рейтинг и CSV-выгрузка |
| Frontend | `frontend/` | Flutter Web UI преподавателя и участника |
| Infrastructure | `docker-compose.yml`, `infra/` | PostgreSQL, Redis, backend, Celery, Flutter web-server |
| Scripts | `scripts/` | Локальные Windows-проверки проекта |
| Docs | `docs/` | Архитектура, roadmap, тестирование, просмотр UI, поддержка |

## Backend слой

Backend построен на Django + DRF + Channels.

- `apps.core` - регистрация/профиль преподавателя, права доступа, канонический адрес клиента и общие Redis-квоты.
- `apps.quiz` - модели и CRUD викторин, вопросов и вариантов ответов.
- `apps.session` - live-сессии, участники, неизменяемые попытки и итоги, команды, WebSocket, правовые сведения и CSV-выгрузка.
- `umclick` - настройки Django, URL routing, ASGI/WSGI, Celery app.

Backend остается Django-монолитом, но приложения уже разделены по предметным областям. Это снижает риск случайного смешивания authentication, quiz CRUD и live game-flow.

## Frontend слой

Frontend построен на Flutter Web.

- `lib/main.dart` - вход в приложение, routing entry points, вкладки teacher/participant.
- `lib/api` - HTTP API client.
- `lib/core` - общие helpers: конфигурация, ролевое хранение, редуктор состояния, контроллеры повторов, WebSocket supervisor, таймер и форматирование.
- `lib/l10n` - текущий слой локализации RU/EN.
- `lib/features/teacher` - панель преподавателя, auth session, quiz draft mapper, teacher widgets.
- `lib/features/participant` - экран участника, join source, participant widgets.
- `lib/features/legal` - legal screens и публичные документы.
- `lib/shared` - общие UI surface widgets.

UI декомпозиция уже доведена до разумного уровня. Новые выносы делаем только при явной боли: дублирование, сложный state-flow, тестируемость или заметный рост файла.

## Данные и состояние

Ключевые сущности backend:

- `Quiz` — стабильная карточка с владельцем, `archived_at` и внешней редакцией формы `content_revision`; изменяемое содержимое в ней не хранится.
- `QuizVersion` — полный снимок содержимого в состоянии `draft` или `fixed`. У карточки не более одного черновика; фиксированная версия неизменяема и может обслуживать несколько сессий.
- `Question` — вопрос одной обязательной `QuizVersion`; порядок уникален внутри версии с проверкой в конце транзакции.
- `Choice` - вариант ответа.
- `LiveSession` — сессия с создателем, публичным UUID `join_token` и PIN, уникальным среди незавершённых сессий; обязательно ссылается на точную фиксированную `quiz_version`, а стабильная карточка доступна через неё.
- `Participant` — участник с необязательной связью с учётной записью; телефон допускает `NULL` и не идентифицирует человека.
- `SessionParticipant` — неизменяемая связь с конкретной сессией, снимок имени и отпечаток токена.
- `SessionDisplayAccess` — отдельная выдача и отзыв доступа показа; срок до часа после завершения.
- `SessionQuestionRun` — запуск конкретного вопроса с исходными и действующими сроками.
- `AnswerAttempt` — неизменяемая уникальная попытка с серверным временем PostgreSQL.
- `FinalAnswer` — единственный неизменяемый итог участия в запуске вопроса.
- `SessionCommand` — применённая команда с идентификатором и версиями состояния.
- `LegacyParticipantAnswer` — сохранённая терминальная история временной схемы А, не участвующая в новой схеме.

Состояния `LiveSession`:

- `waiting` - сессия создана, участники могут подключаться.
- `live` - игра запущена.
- `finished` — сессия завершена; прежнее участие доступно с токеном только для чтения.
- `aborted` — сессия остановлена с той же постоянной защитой истории.

## Real-time слой

WebSocket используется для live-событий внутри сессии:

- `session_started`
- `question_reading_started`
- `question_answering_started`
- `answer_delivery_started`
- `answer_state_changed` — только учётной записи после новой сохранённой попытки
- `question_results_opened`
- `participant_joined`
- `session_finished`
- `session_state`

Backend формирует ролевой payload, frontend применяет его через единый редуктор состояния. `live_socket_connection.dart` обслуживает транспорт, а `live_socket_supervisor.dart` — ограниченное переподключение по точным кодам закрытия.

Redis хранит только общие квоты, WebSocket-аренды и технические сообщения Channels. Игровые попытки, итоги, сроки, рейтинг и история остаются только в PostgreSQL. Аренда не заменяет проверку ролевого доступа: перед каждым реальным событием backend повторно проверяет доступ и строит свежий снимок.

## Сроки и финализация

PostgreSQL хранит сроки чтения, основного приёма, трёхсекундной доставки и результатов. Ручные команды, Celery beat и восстановительное чтение используют одну машину `apps.session.gameplay`; пропущенный срок не пересоздаётся. Восстановительное чтение сначала проверяет срок без исключительной блокировки и только при возможном переходе входит в транзакцию, блокирует сессию и запуск и повторяет проверку. Финализация создаёт по одному `FinalAnswer` и публикует событие только после фиксации.

Ответ сначала проверяет доверенный текущий запуск параметризованным `FOR SHARE`, затем получает `clock_timestamp()` и блокирует конкретное участие. Финализатор использует `FOR UPDATE` той же строки запуска. PostgreSQL остаётся источником истины; канал переносит только имя события и версию схемы, а получатель заново строит ролевой снимок. Ошибки ролевых отправок изолируются после фиксации и журналируются без данных ответа; попытка одной группы не останавливает остальные.

## API границы

В А преподаватель определяется группой `teacher`, администратор — признаком `is_staff`. Проверки ограничивают каждое действие владельцем викторины. Регистрация не выдаёт административных полномочий.

Публичны только ограниченный предпросмотр, правовые сведения и создание участия при открытой регистрации. Имя достаточно для анонимного входа, телефон и согласие необязательны. Ответы и чтение участия требуют `Participant`, показ — отдельного `Display`; JWT используется для учётной записи. Потеря токена зарегистрированного участия даёт 409 без перевыпуска, но собственные профиль и результаты остаются доступны по JWT.

Все маршруты сессий и соединений используют UUID. До первого подтверждения соединение не получает данных; ожидание ограничено 10 секундами. Группы разделены по доступу, состояние формируется заново для получателя после проверки токена. Клиент принимает только схему состояния 2 и не применяет меньшую `state_revision`.

Постоянная защита истории обеспечивается защищёнными связями, ограничениями PostgreSQL, проверками прямых/массовых операций и транзакционными службами. `create_quiz_with_draft` создаёт карточку с первым черновиком; `save_quiz_content` сериализует изменения блокировкой `Quiz` и требует `content_revision`; `create_live_session` под той же блокировкой фиксирует изменённый черновик либо повторно использует последнюю равную фиксированную версию. Все три службы сами проверяют действующую роль преподавателя или администратора. Обычная операция блокирует не всю историю, а только текущий черновик и последнюю фиксацию; список материализует только эффективную версию. Все игровые чтения идут через `session.quiz_version`. Технические номера версий не входят в основной HTTP-договор. Архивные действия и предпросмотр относятся к последующим частям. Точные игровые контракты и границы: [этап А](block-1-stage-a-api.md), [этап Б](block-1-stage-b-api.md) и [этап В](block-1-stage-v-api.md).

## Тестовые границы

Покрытие сейчас разделено на слои:

- backend unit tests для legal/scoring helpers;
- backend API flow tests для основных сценариев;
- backend API regression tests для нетиповых действий;
- frontend pure logic tests;
- frontend widget smoke tests;
- frontend widget interaction/regression tests.

Единая локальная команда:

```powershell
.\scripts\check-all.ps1
```

## Архитектурные принципы

- Сначала сохраняем рабочий MVP, затем улучшаем архитектуру.
- Маленькие логические коммиты.
- Backend domain-flow должен иметь API/regression tests.
- Frontend state-heavy widgets должны иметь widget tests.
- Персональные данные и согласия версионируются явно.
- Документация обновляется вместе с изменением архитектуры или flow.
