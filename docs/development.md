# Локальная разработка umclick в Windows

Локальный контур запускается из корня проекта через `dev.ps1`. Он не использует контейнеры, не управляет системными службами и не обращается к публичному стенду.

## Предварительные требования

- Windows PowerShell 5.1 или PowerShell 7;
- Python 3.12 или 3.13;
- Flutter с входящим в SDK Dart;
- локальный PostgreSQL 16 или 17.

Python, Flutter и PostgreSQL устанавливаются разработчиком отдельно. Сценарий проекта их не устанавливает и не обновляет.

## Одноразовая подготовка Python

Для каждой рабочей копии выполните:

```powershell
.\dev.ps1 setup-python
```

Команда создаёт `backend/.venv`, только если каталога ещё нет, затем устанавливает `backend/requirements-dev.txt` и проверяет обязательные импорты. Существующее окружение используется повторно. Повреждённое окружение или несовместимая версия Python автоматически не удаляются и не пересоздаются.

## Ручная подготовка PostgreSQL

Один раз на компьютере разработчика подготовьте отдельную локальную роль PostgreSQL. Ей нужны только `LOGIN` и `CREATEDB`; права `SUPERUSER`, `CREATEROLE`, `REPLICATION` и `BYPASSRLS` запрещены. Роль не должна владеть служебной базой.

Скопируйте `.env.test.example` в неотслеживаемый `.env.test.local` и заполните все шесть `UMCLICK_TEST_DB_*` локальными значениями. Допустимы только `127.0.0.1`, `localhost` и `::1`. Имя временной базы должно начинаться с `test_umclick_`.

Сценарий не создаёт роль, базу или `.env.test.local` и не выводит пароль.

## Ежедневные команды

```powershell
.\dev.ps1 test-backend
.\dev.ps1 test-frontend
.\dev.ps1 test-all
```

`test-backend` проверяет миграции, выполняет системную проверку Django и запускает полный серверный набор с `--noinput`. Зависимости автоматически не устанавливаются.

`test-frontend` последовательно выполняет:

```text
flutter pub get --enforce-lockfile
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
flutter build web
```

Параметр `-SkipBuild` пропускает сборку, а `-BuildLabel <метка>` задаёт локальную метку web-сборки. Для общего запуска доступен `-SkipFrontendBuild`. При ошибке серверной части `test-all` не запускает клиентскую.

## Диагностика и покрытие

При проблемах выполните:

```powershell
.\dev.ps1 doctor
```

`doctor` только читает состояние: проверяет PowerShell, Python и пакеты в `backend/.venv`, Flutter и Dart, файл `.env.test.local`, импорт реального `umclick.test_settings`, соединение с локальным PostgreSQL 16/17 и права роли. Загруженные переменные и настройки кодировки восстанавливаются после успешного и ошибочного завершения.

Покрытие запускается отдельно:

```powershell
.\dev.ps1 test-backend -Coverage
```

Данные сохраняются в `backend/.coverage`, HTML-отчёт — в `backend/htmlcov`. Следующий запуск покрытия перезаписывает данные и обновляет HTML-отчёт.

## Жизненный цикл и границы

- `backend/.venv` сохраняется в рабочей копии до ручного удаления разработчиком;
- `.env.test.local` и локальная роль сохраняются до ручного изменения;
- постоянная тестовая база не создаётся: Django создаёт временную базу на время тестов и штатно удаляет её;
- после принудительного завершения временная база может остаться; автоматической очистки нет, удаление выполняется вручную только после проверки точного объекта;
- постоянные журналы запусков не создаются;
- слой событий и фоновые задачи в тестовых настройках работают в памяти.

## Типовые ошибки

- «Не найдено `backend/.venv`» — выполните `.\dev.ps1 setup-python`.
- «Не найден `.env.test.local`» — создайте его вручную по примеру.
- Ошибка loopback — проверьте, что указан только локальный адрес.
- Ошибка прав роли — оставьте `LOGIN` и `CREATEDB`, удалив административные права.
- Ошибка версии PostgreSQL — используйте локальный сервер версии 16 или 17.
- Ошибка форматирования — запустите форматирование отдельно, проверьте изменения и повторите тест.

Секреты не передавайте в командной строке и не включайте в сообщения об ошибках.
