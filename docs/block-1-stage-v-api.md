# Контракт этапа В «Интерфейсы, нагрузка и завершение первого блока»

Версия документа: 1.0. Фактическая локальная реализация от 4 сентября 2026 года.

Документ дополняет [контракт данных и доступа А](block-1-stage-a-api.md) и [контракт проведения Б](block-1-stage-b-api.md). PostgreSQL остаётся единственным источником игровых данных. Redis используется только для общих квот, WebSocket-аренд и Channels; ответы, итоги, результаты и история в Redis не переносятся.

Версии, черновики и архивирование викторин в этап В не входят. Их согласованная будущая модель описана отдельно в [документе версий и архивирования](quiz-versioning-and-archiving.md).

## Идентификаторы и доступ

Все HTTP- и WebSocket-маршруты сессии используют публичный строковый UUID `join_token`. Числовой идентификатор сессии во внешний клиентский контракт не входит.

Схемы заголовка `Authorization` разделены:

| Роль | Схема | Назначение |
|---|---|---|
| Учётная запись | `Bearer <JWT>` | Управление собственными викторинами и сессиями |
| Участие | `Participant <секрет>` | Состояние и ответы только конкретного участия |
| Показ | `Display <секрет>` | Состояние только конкретного экрана показа |

Сервер хранит только SHA-256-отпечатки ролевых секретов. В локальном хранилище токен индексируется по роли доступа, UUID сессии и доверенному адресу API (`origin`). На сервере токен связан с конкретной записью доступа, участием и сессией, но не с внешним IP пользователя. Смена сети или внешнего IP сама по себе токен не аннулирует. Токен никогда не передаётся в URL, журнал или сообщение ошибки.

Параметр `api` из join- или display-ссылки игнорируется. Относительный `/api` использует origin открытого приложения; явно заданный разработчиком абсолютный API допускается только с `http`/`https`, непустым host и без `userinfo`.

Участие и показ восстанавливаются после обновления страницы только тогда, когда успешный ответ с исходным токеном уже получен и токен сохранён локально. Создание участия и серверная выдача Display-доступа не идемпотентны: если успешный ответ потерян до сохранения секрета, восстановить его из серверного отпечатка нельзя. Клиент не создаёт новую Display-выдачу при повторном открытии уже сохранённого окна: токен индексируется также по `grant_id`, а преподаватель может отозвать именно эту выдачу. Если всё же запрошена новая выдача, сервер атомарно отзывает прежние активные выдачи сессии.

## HTTP-ошибки

| Ситуация | Статус и тело | Действие клиента |
|---|---|---|
| Конфликт управляющей команды | `409`, `code: state_conflict`, `detail`, обязательный снимок `state` схемы 2 | Применить актуальное состояние, не повторять команду автоматически |
| Обычный конфликт подключения, ответа, рейтинга или другой операции | `409`, `code: conflict`, `detail`; `state` не гарантируется | Не повторять операцию; выполнить не более одного разрешённого чтения актуального состояния |
| Прикладная квота | `429`, `code: rate_limited`, целый `retry_after`; тот же `Retry-After` в заголовке | Ограниченный повтор с прежним идентификатором операции |
| Недоступность обязательного ограничителя | `503`, `code: limiter_unavailable`, `retry_after: 3`; `Retry-After: 3` | Операция не выполняется; допускается ограниченный повтор |
| Ролевой доступ не предъявлен | `401`, `code: access_required` | Показать требование доступа; сохранённый токен не удалять |
| Неверный формат заголовка | `401`, `code: access_malformed` | Показать ошибку формата; сохранённый токен не удалять автоматически |
| Токен другой роли или области | `401`, `code: access_scope_mismatch` | Не раскрывать чужую сессию; сохранённый токен не удалять автоматически |
| Токен однозначно недействителен | `401`, `code: access_invalid` | Удалить только соответствующий сохранённый ролевой токен |
| Display-доступ отозван | `401`, `code: access_revoked` | Удалить соответствующий Display-токен и прекратить соединение |
| Display-доступ истёк | `401`, `code: access_expired` | Удалить соответствующий Display-токен и прекратить соединение |
| Ресурс не найден или скрыт политикой доступа | `404` | Токен не удалять: ответ не доказывает его недействительность |

Прокси-ошибка, неизвестный маршрут и любой 401/404 без одной из трёх однозначных причин `access_invalid`, `access_revoked`, `access_expired` не уничтожают локально сохранённый токен.

## Прикладные квоты HTTP

| Операция | Маршруты | Субъект | Скорость | Запас |
|---|---|---|---:|---:|
| Вход по логину | `POST /api/auth/token/` | Нормализованный логин | 10/мин | 10 |
| Вход по адресу | `POST /api/auth/token/` | Канонический адрес | 60/мин | 30 |
| Поиск по PIN | `GET /api/sessions/join/preview/?pin=…`, `POST /api/sessions/join/` с PIN | Канонический адрес | 60/мин | 120 |
| Создание участия | `POST /api/sessions/join/` без подтверждённого `Participant` | Канонический адрес | 60/мин | 60 |
| Чтение состояния | `GET /api/sessions/{uuid}/state/`, `participation/`, `display-state/`; восстановление через `join/` | Подтверждённая учётная запись или запись ролевого доступа | 5/с | 20 |
| Ответ | `POST /api/sessions/{uuid}/answer/` | Подтверждённое участие | 10/с | 40 |
| Команда | `POST /api/sessions/{uuid}/start/`, `start-quiz/`, `end-question/`, `next-question/`, `finish/` | Подтверждённая учётная запись | 2/с | 10 |

UUID-предпросмотр без PIN не расходует неутверждённую адресную квоту. Подключение с PIN проверяет PIN-квоту и квоту создания одним атомарным решением. Восстановление с подтверждённым `Participant` проверяет PIN и чтение состояния, но не создание нового участия.

## Общий алгоритм Redis

Одна операция стоит 60 000 целых единиц. Скорость задаётся целым числом единиц на миллисекунду; например, 10 запросов в минуту пополняют 10 единиц/мс, а 10 запросов в секунду — 600 единиц/мс.

Каждый Lua-вызов получает время только через Redis `TIME` и для каждого ключа вычисляет:

```text
elapsed_ms = max(0, now_ms - stored_last_ms)
tokens = min(capacity, tokens + elapsed_ms * refill_per_ms)
new_last_ms = max(stored_last_ms, now_ms)
```

Все затрагиваемые запасы проверяются одним атомарным `EVAL`. Если хотя бы одного недостаточно, списание не выполняется ни из одного; `retry_after` округляется вверх до целой секунды. Будущая `stored_last_ms` сохраняется, поэтому управляемая проверка 40/41 не получает случайного пополнения. Сырые логины, IP и токены заменяются HMAC-отпечатками в ключах. Локального резервного счётчика при отказе Redis нет.

## Команды и ответы участника

Тело команды и правила проведения остаются в [контракте Б](block-1-stage-b-api.md). Клиент создаёт один `command_id` для пользовательского намерения и использует неизменное тело при транспортных повторах.

| Исход команды | Повторы | Результат интерфейса |
|---|---|---|
| `200` | Нет | Применяется только валидное состояние схемы 2; затем выполняется контрольное чтение |
| `409 state_conflict` | Нет | Снимок `state` применяется сразу; пользователь видит конфликт актуального состояния |
| Обычный `409 conflict` | Нет; одно чтение состояния | Показывается отказ операции, интерфейс синхронизируется, если чтение удалось |
| `429` | Не более трёх повторов по каждому серверному `retry_after` | Тот же `command_id`; после исчерпания — временная ошибка |
| `503` | Не более трёх повторов по каждому серверному `retry_after`; при отсутствии корректного значения — по 3 секунды | Тот же `command_id`; после исчерпания — временная ошибка |
| Сетевой разрыв | Не более трёх повторов через 1, 2 и 4 секунды, затем одно чтение | Если ожидаемое состояние уже достигнуто — успех после восстановления; иначе результат остаётся неопределённым |

Повтор команды отменяется при изменении ревизии, статуса, фазы или `question_run_id`, при новом намерении либо закрытии экрана. Неопределённую команду можно повторить из интерфейса только с сохранённым прежним `command_id`, пока контекст не изменился.

Ответ участника содержит только `question_id`, `choice_id`, `submission_id`. HTTP 200 — нейтральное подтверждение доставки; он не сообщает правильность и сам по себе не доказывает включение в итог.

| Исход ответа | Повторы | Результат интерфейса |
|---|---|---|
| `200` | Нет | Выбор помечается доставленным без раскрытия правильности |
| Обычный `409 conflict` | Нет; одно ролевое чтение | Показывается конфликт, применяется доступное актуальное состояние |
| `429` | Не более трёх повторов по `retry_after` | Тот же `submission_id`; после исчерпания запрос остаётся доступен как неопределённый повтор |
| `503` | Не более трёх повторов по каждому серверному `retry_after`; при отсутствии корректного значения — по 3 секунды | Тот же `submission_id`; после исчерпания — временная ошибка |
| Сетевой разрыв | Не более трёх повторов через 1, 2 и 4 секунды, затем одно чтение | Совпавший `selected_choice_id` подтверждает восстановление; иначе результат неопределён |
| Новый выбор во время ожидания | Старый результат отменяется; активные HTTP-передачи не выполняются параллельно | Новый выбор получает новый `submission_id`; старый ответ больше не меняет интерфейс |

Повтор ответа прекращается при новом выборе, изменении состояния вопроса/фазы/ревизии, смене запуска или закрытии экрана. Неопределённый повтор того же выбора сохраняет прежний `submission_id`.

Обычный HTTP-запрос ограничен 10 секундами на получение заголовков и тела целиком, выгрузка CSV — 30 секундами. Новое намерение отменяет предыдущую HTTP-передачу; в один момент контроллер отправляет не более одной команды либо одного ответа. Поколение намерения и контекст проверяются после каждой асинхронной границы, поэтому просроченный ответ, ошибка или дополнительное чтение отменённой операции не меняют интерфейс.

## WebSocket

Маршрут: `/ws/sessions/{uuid}/`. Flutter проверяет строгий UUID до открытия соединения. Если путь не совпал с маршрутом или handshake отклонён до `accept()`, сервер не обещает JSON `connection_error` и наблюдаемый код 4000; клиент обрабатывает это как ошибку установления соединения.

После успешного `accept()` клиент за 10 секунд должен отправить единственное первое сообщение:

```json
{"event":"auth","access_type":"account|participant|display","token":"<секрет>"}
```

До подтверждения доступа снимок состояния и игровые события не отправляются. После авторизации первое сообщение — `session_state` схемы 2. Любое реальное игровое событие вызывает повторную проверку доступа и сборку свежего ролевого снимка из PostgreSQL.

| Причина после `accept()` | Код закрытия | Безопасное сообщение | `retry_after` | Поведение Flutter |
|---|---:|---|---:|---|
| Некорректный протокол/JSON | 4000 | `protocol_error` | — | Не повторяет |
| Доступ не подтверждён за 10 с | 4001 | `auth_timeout` | — | Не повторяет |
| Неверный формат, роль, область, недействительность, отзыв или истечение ролевого доступа | 4003 | Соответствующий `access_*` | — | `Participant`/`Display` не повторяет и удаляет токен только для `access_invalid/revoked/expired`; преподаватель при `access_expired` однократно обновляет JWT через общий координатор единственного запроса (`single-flight`) и пересоздаёт соединение, если refresh ещё действителен |
| Частота открытия или сообщений | 4429 | `rate_limited` | Да | До трёх повторов по `retry_after`, затем прекращает |
| Превышение 3/120/240 соединений | 4429 | `connection_limit` | Да | Повторяет только новое соединение до трёх раз; существующие не вытесняются |
| Сообщение больше 16 КиБ | 1009 | `message_too_large` | — | Не повторяет |
| Redis недоступен или аренда потеряна | 4503 | `limiter_unavailable` | 3 | До трёх повторов через 3, 6 и 12 с, затем прекращает |
| Транспортный разрыв, 1006 или перезапуск 1012 | Код может отсутствовать | JSON не гарантируется | — | Шесть повторов через 1, 2, 4, 8, 16 и 30 с с разбросом ±20%, затем прекращает |
| Нормальное закрытие или другой терминальный код | Фактический код | По ситуации | — | Не повторяет |

Пределы: открытие 10/с с запасом 60; не более 3 соединений на одну запись доступа, 120 на канонический адрес и 240 на экземпляр стенда; сообщения 5/с с запасом 20; входящее сообщение не более 16 КиБ. Аренда обновляется каждые 15 секунд и истекает через 45 секунд. Все операции аренды используют Redis `TIME` и атомарно затрагивают ключи доступа, адреса и стенда. Redis-heartbeat не обращается к PostgreSQL.

Фоновая проверка доступа больше не строит полное состояние каждую секунду. Она распределена на 45–75 секунд и выполняет один SQL `EXISTS` на роль. JWT и завершённый Display имеют отдельный таймер до точного срока. Перед реальным событием полная проверка выполняется немедленно. HTTP- и WebSocket-ограничители процесса совместно используют один Redis-клиент и пул для каждого точного URL; тестовые клиенты и пространства остаются изолированными.

## Nginx

В группу входа входят только:

- `POST /api/auth/register/`;
- `POST /api/auth/token/`;
- `POST /api/auth/token/refresh/`;
- `GET /api/sessions/join/preview/`;
- `POST /api/sessions/join/`.

Любой другой не-`OPTIONS` запрос `/api/**` входит в игровую группу. Статические файлы, `/ws/**` и `OPTIONS` в HTTP-зоны не входят.

Для входа действуют независимые зоны 10/с на адрес с запасом 120 и 30/с на экземпляр с запасом 240. Для игрового API — 100/с на адрес с запасом 300 и 200/с на экземпляр с запасом 600. Все зоны используют `nodelay`. Общий ключ экземпляра — непустая константа конфигурации стенда.

Только собственный ответ Nginx 429 получает `Retry-After: 1`. `proxy_intercept_errors off` сохраняет динамический `Retry-After` от Django. Nginx перезаписывает `X-Real-IP` и `X-Forwarded-For` фактическим `$remote_addr`; backend доверяет их только если непосредственный peer входит в явно настроенный `TRUSTED_PROXY_CIDRS`. Конкретное значение для стенда не задано до проверки его сети.

Demo Compose публикует только порт frontend, а backend не имеет `ports`. Это статическое ограничение конфигурации; невозможность прямого внешнего доступа и фактическая работа Nginx должны проверяться из независимого узла после отдельного разрешения на стенд.

## Состояние, экран показа и рейтинг

Flutter принимает только `schema_version: 2`, совпадающий UUID и целую неотрицательную `state_revision`. Снимок с меньшей ревизией игнорируется; снимок той же ревизии не может заменить стабильные статус, фазу и текущий запуск противоречивыми значениями. На участнике поле `answer.answer_version` монотонно упорядочивает собственный ответ внутри той же общей ревизии: запоздавший снимок не откатывает локально выбранный вариант. Счётчики при равной ревизии также не уменьшаются. Новый `question_run_id` немедленно удаляет ответ предыдущего запуска.

Экран показа использует только собственный Display-токен и не зависит от короткого JWT преподавателя. Открытие или закрытие окна не отправляет игровых команд. UUID выдачи хранится вместе с токеном; преподаватель может идемпотентно отозвать точную выдачу. Пьедестал показывает все строки с рассчитанным `rank <= 3`, а не первые три элемента массива.

Рейтинг новой схемы не содержит баллов. Порядок: число правильных итогов по убыванию, затем сумма `correct_time_ms` только правильных итогов по возрастанию. Время отображается с тремя знаками после запятой, поэтому 40,234 и 40,432 секунды различаются. Те же поля используются в интерфейсе, истории и CSV.

## Эксплуатационная граница

Команда `stage_v_game_data` отдельно поддерживает инвентаризацию, пробный транзакционный откат и защищённую очистку согласованных игровых таблиц с сохранением учётных записей, ролей, входа и истории миграций. Обычный запуск, сборка и миграции очистку не вызывают. Точный порядок и восстановление приведены в [инструкции развёртывания](deployment.md).
