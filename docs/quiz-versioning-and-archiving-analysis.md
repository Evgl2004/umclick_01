## 1. Краткий вывод о готовности к реализации и исходное состояние

### Вывод

Согласованная бизнес-модель реализована локально без отдельного хранилища снимков, глобальной дедупликации, распределённых блокировок, новых очередей или изменения игровой схемы событий. Части 1–4 приняты и зафиксированы отдельными локальными коммитами; часть 5 выполнена как однобазовая локальная репетиция перехода, очистки, восстановления и сохранности учётной записи. После репетиции выделенная тестовая база возвращена к исходному логическому состоянию. Публикация и обновление рабочего сервера не выполнялись и остаются отдельными действиями.

Минимальная безопасная модель:

- `Quiz` остаётся стабильной карточкой и хранит владельца, архивное состояние и маркер актуальности формы;
- `QuizVersion` хранит всё содержимое и имеет состояние `draft` или `fixed`;
- `Question` принадлежит версии, а `Choice` — вопросу;
- `LiveSession` ссылается только на одну зафиксированную `QuizVersion` с запретом удаления;
- все изменяющие операции одной карточки сериализуются блокировкой строки `Quiz` в PostgreSQL;
- устаревшие сохранения различаются отдельным `content_revision`, который не является ни номером версии содержимого, ни игровым `state_revision`;
- старые игровые данные не преобразуются и не удаляются миграцией: перед структурным переключением применяется уже существующая контролируемая очистка после отдельной проверки и резервного копирования.

Главный риск не в добавлении таблицы, а в неполном переключении чтений. Сейчас название, настройки, вопросы и таймеры читаются из `session.quiz` во многих путях: управление игрой, автоматические переходы, снимки преподавателя/участника/показа, публичный вход и история. Если заменить только внешний ключ, старая сессия всё равно сможет получить новое содержимое либо часть игрового кода перестанет работать. Семантическое переключение этих путей и защита неизменяемых строк образуют одну неделимую серверную часть.

## 3. Карта текущих зависимостей и целевая модель данных

### 3.1. Текущее состояние: факты

Сейчас одна строка `Quiz` одновременно является карточкой и изменяемым содержимым: владелец, название, описание, настройки показа, времена и служебные даты находятся в `backend/apps/quiz/models.py:10-37`. `Question.quiz` каскадно ссылается на карточку, `Choice.question` — на вопрос (`models.py:40-86`).

Текущая историческая цепочка:

```text
Quiz
├── Question
│   └── Choice
└── LiveSession (PROTECT)
    ├── current_question -> Question (PROTECT)
    ├── current_run -> SessionQuestionRun (PROTECT)
    ├── SessionQuestionRun -> Question (PROTECT)
    ├── AnswerAttempt -> Choice (PROTECT)
    └── FinalAnswer -> попытки + снимок is_correct/времени
```

`LiveSession.quiz` ссылается непосредственно на `Quiz` (`backend/apps/session/models.py:54-82`). Проверки `LiveSession.save`, `SessionQuestionRun.save`, `LegacyParticipantAnswer.save` и `AnswerAttempt.save` удостоверяют принадлежность вопроса/варианта этой карточке (`models.py:96-154,244-253,333-350,389-401`).

Любая существующая сессия делает всю карточку неиспользуемой для редактирования: `ensure_unused` ищет `LiveSession` любого статуса по `quiz_id`, а `Quiz.save`, `Question.save`, `Choice.save`, удаления и административные формы вызывают эту проверку (`backend/apps/core/protection.py:42-71`, `backend/apps/quiz/models.py:29-37,53-61,78-86`, `backend/apps/quiz/admin.py:11-32`). Это защищает историю, но противоречит новой возможности редактировать будущий запуск через новую версию.

Вложенный сериализатор разрешает обновлять вопрос/вариант только по идентификатору из текущей карточки, перенумеровывает массивы и удаляет пропущенные элементы (`backend/apps/quiz/serializers.py:49-118`). Это полезная проверка принадлежности, но её граница должна стать конкретной версией, а не карточкой.

### 3.2. Целевая схема: предложение

#### `quiz_quiz` / `Quiz` — стабильная карточка

| Поле | Назначение |
|---|---|
| `id` | Стабильный существующий идентификатор, который продолжает выбирать преподаватель и передавать при создании сессии. |
| `owner_id` | `PROTECT` на пользователя; текущая модель прав сохраняется. |
| `archived_at` | `NULL` для рабочего списка, время для архива. Отдельный дублирующий `is_archived` не нужен. |
| `content_revision` | Неотрицательный счётчик актуальности формы; начальное значение 1, увеличивается только при содержательном сохранении. |
| `created_at`, `updated_at` | Служебные даты карточки. |

Название и остальные поля содержимого из `Quiz` удаляются после переключения. `content_revision` — внешний маркер оптимистической конкуренции, но не номер `QuizVersion`. Архивирование/восстановление и фиксация версии не меняют его, потому что содержимое формы не меняется.

#### `quiz_quizversion` / `QuizVersion` — состояние содержимого

| Поле | Назначение |
|---|---|
| `id` | Внутренний первичный ключ; в основном интерфейсе и обязательном пользовательском вводе не появляется. |
| `quiz_id` | `CASCADE` на стабильную карточку. Каскад допустим только для карточки без сессий. |
| `number` | Внутренний последовательный номер внутри карточки, назначаемый под блокировкой карточки. |
| `status` | `draft` или `fixed`. |
| `fixed_at` | `NULL` у черновика, время фиксации у неизменяемой версии. |
| `title`, `description` | Содержимое конкретного состояния. |
| `question_only_on_display`, `show_choices_on_participant` | Настройки показа конкретного состояния. |
| `reading_time_sec`, `results_time_sec` | Временные настройки конкретного состояния. |
| `created_at`, `updated_at` | Диагностические даты версии. |

Ограничения БД:

- уникальность `(quiz_id, number)`;
- условная уникальность `quiz_id WHERE status = 'draft'`, гарантирующая не более одного черновика;
- проверка `status = 'fixed'` тогда и только тогда, когда `fixed_at IS NOT NULL`;
- положительный `number` и существующие диапазоны времени подтверждаются модельной/сериализаторной валидацией; для диапазонов можно сохранить существующие проверки приложения, не вводя новый набор дублирующих ограничений в этом изменении.

Отдельные `current_draft_id` и `latest_fixed_id` на карточке не нужны. Текущий черновик получается условно-уникальным запросом по `status='draft'`; последняя фиксация — по максимальному `number` среди `fixed`. Отсутствие дублирующих указателей исключает рассогласование и циклические внешние ключи.

Хеш содержимого также не обязателен. Для доказуемого повторного использования нужно сравнивать каноническое содержимое текущего черновика с последней зафиксированной версией той же карточки. Каноническое представление включает название, описание, оба флага, оба времени, упорядоченные вопросы и варианты, но исключает первичные ключи и служебные даты. Такое сравнение локально карточке, не является глобальной дедупликацией и не создаёт коллизионной границы истинности.

Кардинальности целевой схемы:

```text
Quiz 1 ── 0..N QuizVersion
             ├── одновременно 0..1 draft
             └── 0..N fixed
QuizVersion 1 ── 1..N Question ── 2..N Choice
QuizVersion(fixed) 1 ── 0..N LiveSession
LiveSession 1 ── 0..N SessionQuestionRun ── 1 Question этой же версии
SessionQuestionRun 1 ── 0..N AnswerAttempt ── 1 Choice своего вопроса
SessionQuestionRun 1 ── 0..N FinalAnswer ── 0..1 выбранная и 0..1 временная попытка
```

Минимумы вопросов/вариантов задаются существующей содержательной валидацией, а не самой связью внешнего ключа. `fixed` без сессии возможен только как промежуточное состояние внутри ещё не завершившейся транзакции создания сессии; после фиксации транзакции такая строка не должна существовать.

#### `quiz_question` / `Question`

- заменить `quiz_id` на обязательный `quiz_version_id` с `CASCADE`;
- сохранить `text`, `order`, `time_limit_sec`;
- добавить откладываемую до конца транзакции уникальность `(quiz_version_id, order)`, чтобы итоговый порядок был целостным, а перестановка существующих строк внутри одной транзакции не падала на промежуточном совпадении;
- запретить перенос существующей строки в другую версию.

#### `quiz_choice` / `Choice`

- сохранить внешний ключ `question_id` с `CASCADE`, `text`, `is_correct`, `order`;
- добавить откладываемую уникальность `(question_id, order)`;
- запретить перенос существующего варианта в другой вопрос;
- принадлежность версии выводится только через вопрос; дублирующий `quiz_version_id` не нужен.

#### `session_livesession` / `LiveSession`

- заменить `quiz_id` на обязательный `quiz_version_id` с `PROTECT`;
- не хранить параллельно второй внешний ключ на `Quiz`: это создало бы два источника принадлежности без межтабличного ограничения, гарантирующего их равенство;
- стабильная карточка доступна через `session.quiz_version.quiz`, а существующее внешнее поле ответа `quiz.id` формируется из этой карточки;
- `current_question_id`, `current_run_id`, `revealed_question_id`, `join_token`, PIN, статусы, фазы, `state_revision`, `gameplay_schema` и сроки сохраняют смысл.

`LiveSession` может ссылаться только на `fixed`. Межтабличный `CHECK` в PostgreSQL этого не выражает; поэтому поддерживаемое создание выполняет только единая служба `create_live_session(quiz_id, actor, ...)`, а прямые `LiveSession.save(force_insert=True)` и `LiveSession.objects.create(...)` запрещаются. Служба сама проверяет владельца или административную роль, архив карточки, принадлежность выбранной версии этой карточке и состояние `fixed` под общей блокировкой `Quiz`. Триггер БД не добавляется без отдельного требования.

#### Остальные исторические связи

`SessionQuestionRun.question`, `LegacyParticipantAnswer.question/choice`, `AnswerAttempt.choice`, `FinalAnswer.selected_attempt/timing_attempt` сохраняются. Их `PROTECT`-ссылки вместе с `LiveSession.quiz_version` удерживают точные исторические строки. Проверки принадлежности меняются так:

- текущий вопрос и вопрос запуска должны принадлежать `session.quiz_version_id`;
- вариант попытки должен принадлежать вопросу запуска;
- вариант устаревшего ответа должен принадлежать его вопросу, а вопрос — версии сессии;
- `FinalAnswer.is_correct` и времена остаются зафиксированным итогом и не пересчитываются из нового черновика.

### 3.3. Идентификаторы при создании нового черновика

После первой сессии использованный черновик становится `fixed`; его вопросы и варианты менять или повторно использовать как строки нового черновика нельзя. Первое последующее содержательное сохранение выполняется так:

1. Под блокировкой карточки определяется последняя зафиксированная версия и отсутствие текущего черновика.
2. Все переданные идентификаторы вопросов проверяются на принадлежность именно этой исходной версии; идентификаторы вариантов — именно переданному исходному вопросу. Дубликаты и чужие идентификаторы дают 400 до изменения данных.
3. Создаётся `QuizVersion(status='draft', number=last+1)`.
4. Вопросы копируются с новыми первичными ключами. В памяти транзакции строится `old_question_id -> new_question_id`.
5. Варианты копируются с новыми первичными ключами и привязываются через это соответствие. Аналогичное соответствие вариантов существует только до применения тела запроса.
6. Изменения формы применяются к новым строкам. Удалённые элементы удаляются только из нового черновика; новые элементы с `id = null` создаются.
7. Полный новый черновик валидируется, `content_revision` увеличивается, ответ возвращает новые идентификаторы, которыми клиент заменяет локальные.

Отдельную таблицу происхождения идентификаторов хранить не требуется: пользователь не выбирает версии и бизнес-функции сравнения версий нет. При существующем черновике идентификатор допустим только из него. Идентификатор из старой фиксированной или чужой версии всегда отвергается, поэтому редактор не может изменить историю по старому ключу.

Текущий клиент идентификаторы вопросов/вариантов теряет: классы формы их не содержат, а `QuizDraftMapper.fromMap/toPayload` не переносит (`frontend/lib/features/teacher/quiz_draft.dart:3-35`, `quiz_draft_mapper.dart:48-105,133-198`). Это не подходит целевой операции копирования. В будущем в локальные модели добавляются необязательные `id`, а в `QuizDraftData` — `contentRevision`; это технические ключи строк текущей формы, не показываемые пользователю.

### 3.4. Индексы

Достаточный начальный набор без недоказанной оптимизации:

- автоматические индексы внешних ключей `Quiz.owner`, `QuizVersion.quiz`, `Question.quiz_version`, `Choice.question`, `LiveSession.quiz_version`;
- уникальный индекс `(quiz_id, number)`;
- условный уникальный индекс одного черновика;
- откладываемые уникальные индексы порядка вопросов и вариантов;
- существующие индексы/ограничения PIN, UUID, запусков, попыток и команд сохраняются.

Для проверки архива запрос сначала получает версии карточки по индексированному `QuizVersion.quiz_id`, затем сессии по индексированному `LiveSession.quiz_version_id` и фильтрует два статуса. Отдельный составной или частичный индекс на открытые сессии сейчас не доказан объёмом или планом запроса. Его следует добавлять только после измерения `EXPLAIN` на реальном масштабе, а не как часть этой модели по умолчанию. То же относится к отдельным индексам рабочего/архивного списка.

## 4. Операции, транзакции, конкретные конкурентные сценарии и стоимость

### 4.1. Общий порядок блокировок

Для операций карточки вводится единый порядок:

```text
Quiz (SELECT ... FOR UPDATE)
→ нужные QuizVersion в порядке id
→ при архивировании/удалении связанные LiveSession в порядке id
```

Путь приёма ответа этот порядок не использует и не должен начинать блокировать карточку. В нём сохраняется принятый порядок: параметризованный SQL блокирует текущий `SessionQuestionRun` через `FOR SHARE OF run`, затем берётся `clock_timestamp()`, серверный контекст проверяется повторно, после чего блокируется участие (`backend/apps/session/gameplay.py:44-130`). Финализатор по-прежнему блокирует `LiveSession`, затем текущий запуск `FOR UPDATE` (`gameplay.py:197-205,392-423,474-493`). Замена источника вопросов/таймеров не должна менять эту конкуренцию.

### 4.2. Операции

#### Создание карточки

В одной `transaction.atomic` создаются `Quiz(content_revision=1)`, черновик № 1, вопросы и варианты. Ошибка вложенной валидации откатывает всё. Публичного PIN, сессии и исторической версии нет.

#### Сохранение

1. До транзакции проверяется только структура типов и строится нормализованное тело; решение о равенстве и принадлежности идентификаторов здесь не принимается.
2. В `transaction.atomic` карточка выбирается по правам владельца/администратора с `FOR UPDATE`.
3. Повторно проверяется, что карточка не архивна.
4. Переданный `content_revision` сравнивается с текущим. Несовпадение даёт 409 до проверки содержательного равенства и до любых записей.
5. Блокируются текущий черновик и последняя фиксация. Базой редактора является черновик, если он существует, иначе последняя фиксация.
6. До любого раннего успеха проверяются все переданные идентификаторы: id вопросов уникальны и принадлежат базе; id вариантов уникальны, принадлежат указанному вопросу и той же базе; новый вопрос не может ссылаться на старый вариант. Чужой, повторный или несовместимый id даёт 400 без записи.
7. Для `PATCH` нормализованное тело сначала объединяется с базой; затем строятся два канонических представления без id и служебных дат.
8. Если итог канонически равен базе, одинаково для существующего черновика и для одной последней фиксации возвращается текущая структура с теми же дочерними id и тем же `content_revision`. Версия не создаётся, строки не заменяются, счётчик не увеличивается.
9. Если содержимое реально изменилось и черновик уже есть, служба изменяет только этот черновик; новая версия не создаётся.
10. Если содержимое реально изменилось и черновика нет, создаётся новый черновик и новые дочерние ключи по алгоритму раздела 3.3.
11. Полный итог валидируется, все дочерние изменения завершаются, после чего `content_revision` увеличивается ровно на один в той же транзакции. Клиент получает полное актуальное содержимое и, только если они действительно появились, новые ключи.

Порядок `права/архив → ревизия → принадлежность и уникальность id → каноническое равенство → запись` обязателен. Поэтому сравнение без идентификаторов не позволяет принять подставной id, а совпадающее тело устаревшей вкладки не отменяет 409 и не выдаётся за успешное сохранение.

Отдельные будущие сценарии для этой развилки:

- идентичное сохранение существующего черновика сохраняет номер версии, все id и ревизию;
- идентичное сохранение при отсутствии черновика не создаёт его и возвращает id последней фиксации;
- реальное изменение существующего черновика увеличивает ревизию один раз без новой версии;
- реальное изменение после фиксации создаёт один новый черновик с новыми id и увеличивает ревизию один раз;
- любое из четырёх тел с устаревшей ревизией получает 409 до сравнения;
- актуальная ревизия с чужим или повторным id получает 400 даже при канонически одинаковом тексте.

#### Простой предпросмотр

Рекомендуемый вариант не делает серверного запроса и не открывает транзакцию. Клиент строит нормализованное представление из текущих контроллеров формы, выполняет ту же содержательную валидацию, открывает локальный экран и после закрытия возвращается к тем же объектам формы. Ни `QuizVersion`, ни сессия, ни PIN/QR, ни доступ показа, ни участник, ни ответ не создаются.

#### Создание обычной сессии

Создание переносится из простого `ModelSerializer.save` в явную доменную службу:

1. В `transaction.atomic` карточка владельца/администратора блокируется по стабильному `quiz_id`.
2. Проверяется `archived_at IS NULL`.
3. Блокируются текущий черновик и последняя фиксация; определяется эффективное содержимое.
4. Если черновик отличается от последней фиксации либо фиксации ещё нет, черновик полностью валидируется и переводится в `fixed` с `fixed_at`.
5. Если черновик канонически равен последней фиксации, сессия использует последнюю фиксацию, а одинаковый редактируемый черновик остаётся черновиком: это сохраняет актуальные ключи открытого редактора.
6. Если черновика нет, повторно используется последняя фиксация.
7. `LiveSession` создаётся с `quiz_version_id` в той же транзакции; генерация уникального PIN сохраняет текущие ограничение и повтор попытки.

Если создание сессии или PIN окончательно завершается ошибкой, перевод черновика в `fixed` откатывается вместе с сессией. Границей фиксации остаётся именно успешное создание обычной сессии, а не старт игры.

#### Архивирование

Карточка блокируется; по всем её версиям выбираются и блокируются сессии со статусом `waiting` или `live`. Наличие хотя бы одной даёт 409 и точный текст `Сначала завершите или остановите открытую сессию`. `finished` и `aborted` не блокируют. При успехе ставится `archived_at`; версии и история не меняются. Повторное архивирование рекомендуется сделать идемпотентным: вернуть текущее состояние 200 без новой сущности.

#### Восстановление

Карточка блокируется, `archived_at` очищается. Версии и сессии не меняются. Если черновика нет, первое содержательное сохранение создаст его из последней фиксации. Повторное восстановление также может быть идемпотентным 200.

#### Физическое удаление

Карточка блокируется и проверяется отсутствие `LiveSession` по всем версиям вне зависимости от статуса. Только затем удаление каскадирует в черновик/версии/вопросы/варианты. Любая историческая сессия даёт 409. `PROTECT` от `LiveSession` к `QuizVersion` остаётся второй линией защиты, если прикладная проверка пропущена.

### 4.4. Стоимость и запросы

- Первый запуск изменённого черновика не копирует вопросы: его строки фиксируются на месте.
- Первое содержательное сохранение после использования один раз копирует `O(Q + C)` строк, где `Q` — вопросы, `C` — варианты, и затем изменяет новый черновик.
- Повторный запуск без изменений не копирует данные и вставляет только сессию с уже существующим `quiz_version_id`.
- Сравнение неизменённости затрагивает текущий черновик и только последнюю фиксацию этой же карточки. Все вопросы и варианты выбираются через `prefetch_related`; запрос на каждый дочерний элемент недопустим.
- Списки карточек должны вычислять эффективное содержимое (черновик, иначе последняя фиксация) заранее выбранными связями, а `can_delete` — одним `Exists` по сессиям, а не отдельным запросом на строку.
- Игровые функции меняют `session.quiz.questions` на заранее выбранную `session.quiz_version.questions`, а времена — на поля версии. Приём ответа не получает новых запросов к карточке.
- Текущие исторические нагрузочные прогоны не назначаются автоматически: алгоритм блокировок ответа/финализатора не меняется. Обязательны целевые PostgreSQL-тесты конкуренции сохранения/фиксации/архива. Повтор старого нагрузочного профиля нужен только если реализация фактически затронет SQL приёма попыток или финализации.

## 5. Договор API, интерфейс, предпросмотр и совместимость

### 5.1. Значения идентификаторов и счётчиков

- `quiz.id` остаётся стабильным идентификатором карточки. Именно его передаёт преподаватель в `POST /api/sessions/`.
- `QuizVersion.id` и `QuizVersion.number` внутренние; основной клиент их не выбирает и не показывает.
- `content_revision` — маркер актуальности редактируемой формы, обязательный при `PUT/PATCH` существующей карточки.
- `state_revision` остаётся монотонной ревизией игрового состояния и используется только командами/снимками сессии. Код `state_conflict` не переиспользуется для сохранения викторины.

### 5.2. Таблица маршрутов

Префикс `/api` задан корневым маршрутизатором; ниже приведены полные внешние пути.

`can_delete` — вычисляемое сервером удобство интерфейса, а не полномочие: между чтением списка и удалением может появиться сессия, поэтому `DELETE` всегда повторяет транзакционную проверку.

### 5.3. Ошибки и сохранность формы

Текущий сервер умеет возвращать `code/detail` для 409 (`backend/apps/core/errors.py:9-31,72-99`), а клиент сохраняет `code`, но общий пользовательский преобразователь обычно показывает английскую служебную строку операции и не извлекает `detail` (`frontend/lib/api/api_client.dart:224-244`, `frontend/lib/shared/user_error_text.dart:20-55`). Это нужно изменить.

Рекомендуемый ответ устаревшего сохранения:

```json
{
  "code": "quiz_revision_conflict",
  "detail": "Викторина уже изменена в другой вкладке. Ваши правки остались в форме; обновите данные перед повторным сохранением.",
  "current_content_revision": 7
}
```

Клиент при этом:

- прекращает индикатор загрузки;
- показывает `detail`;
- не вызывает `_refreshQuizzes`, `_loadQuizDraftFromMap` или сброс контроллеров;
- предлагает отдельное осознанное действие «Загрузить актуальную версию». Автоматического слияния или перезаписи нет в текущем объёме.

Для архива отображается серверный текст `Сначала завершите или остановите открытую сессию`. Новые коды конфликтов не подменяют `state_conflict`, потому что последний содержит снимок игрового состояния и обрабатывается `SessionCommandController` специально.

### 5.4. Интерфейс преподавателя

Текущий интерфейс содержит один выпадающий список, действия «сохранить/новый/обновить/удалить» и отдельную карточку создания сессии (`teacher_quiz_builder_card.dart:145-195,292-345,693-755`). Целевое минимальное изменение:

- переключатель «Рабочие» / «Архив» над списком;
- в рабочем списке — «Архивировать», а «Удалить навсегда» доступно только при `can_delete` и требует подтверждения;
- в архиве — «Восстановить»; редактирование и создание сессии отключены;
- после успешного архивирования карточка удаляется из рабочего списка, но история сессий остаётся;
- после 409 текущий редактор и выбор не сбрасываются;
- после успешного сохранения клиент заменяет локальные дочерние id и `content_revision` значениями ответа;
- номера/идентификаторы `QuizVersion` нигде в основном сценарии не появляются.

История сейчас выводит `session['quiz']['title']` (`frontend/lib/features/teacher/teacher_panel.dart:2028-2058`). Внешняя форма ответа сохраняется, но сервер обязан наполнять её названием зафиксированной версии.

### 5.5. Предпросмотр

Реализован клиентский локальный предпросмотр несохранённых значений формы:

- кнопка располагается рядом с сохранением в конструкторе;
- перед открытием используется та же нормализация и валидация, что перед сохранением, но сетевой вызов не выполняется;
- при неполном/невалидном вопросе предпросмотр не открывается, пользователь получает те же локализованные ошибки, а введённые значения остаются;
- экран позволяет переключать вопрос, вид «экран аудитории» / «экран участника» и состояния чтения / ответа / показа результата;
- `question_only_on_display` и `show_choices_on_participant` применяются; `is_correct` не показывается в состояниях до результата;
- таймеры не запускают игровой автомат, ответы не вводятся и не сохраняются;
- используются чистые виджеты представления, но не `LiveSession`, WebSocket, PIN, QR, публичная ссылка, `SessionParticipant`, `AnswerAttempt` или `FinalAnswer`;
- закрытие возвращает к тем же контроллерам редактора.

Такой вариант соответствует утверждённому действию «предпросмотр из конструктора» и исключает скрытое автосохранение. Проверенная реализация и отклонённая альтернатива приведены в разделах 10 и 9 соответственно.

### 6.2. Защита поддерживаемых прикладных операций

Существующий `GuardedQuerySet` полностью запрещает `update`, `bulk_update`, `bulk_create`, а перед удалением блокирует карточки (`backend/apps/core/protection.py:9-39`). Разрешать отдельные `Question.save`/`Choice.save` для черновика нельзя: такая запись не знает ревизию всей формы и оставляет описанную в Б4-А2 возможность незаметной перезаписи. Минимальный общий порядок следующий.

1. Единственный поддерживаемый путь изменения содержимого — служба `save_quiz_content(quiz_id, actor, expected_content_revision, payload)`. Создание карточки выполняет соседняя служба `create_quiz_with_draft(...)`; фиксация — `create_live_session(...)`.
2. Служба открывает одну `transaction.atomic`, выбирает `Quiz` владельца/администратора с `FOR UPDATE`, повторно проверяет архив и `content_revision`, затем блокирует нужные версии. Все дочерние записи выполняются внутри этой транзакции локальным непубличным записывающим адаптером приложения `quiz`.
3. Публичные `save/delete` существующих `QuizVersion`, `Question`, `Choice`, а также их прямое создание, перенос родителя и массовые `update/bulk_update/bulk_create` отклоняются. Это одинаково относится к черновику и фиксации: внешний одиночный вызов не может атомарно проверить весь граф и увеличить общий счётчик ровно один раз.
4. Непубличный адаптер не является отдельной универсальной системой полномочий: это узкая внутренняя часть `apps.quiz.services`, которой пользуются только три названные службы. Произвольное обращение к нему, как и привилегированный SQL, находится вне поддерживаемого прикладного договора.
5. `content_revision` увеличивается один раз и только после успешной содержательной валидации всех изменений; ошибка любой дочерней записи откатывает дочерние строки и счётчик вместе. Идентичное сохранение не увеличивает его.
6. Административный интерфейс Django показывает версии, вопросы и варианты только для чтения. Архивирование, восстановление и физическое удаление вызывают те же доменные службы; отдельного административного пути редактирования содержимого нет. Если такая возможность понадобится позже, форма обязана передавать актуальный `content_revision` той же службе, а не сохранять вложенные модели отдельно.
7. `Quiz.save` не позволяет напрямую менять владельца, `archived_at` или `content_revision`; создание, архивирование, восстановление и удаление проходят через службы. Прямой `Quiz.delete` и `QuerySet.delete` либо делегируют общей операции удаления, либо отклоняются, но не выполняют собственный каскад без проверки всех версий.
8. Новую `LiveSession` создаёт только `create_live_session(...)`. Прямые `save(force_insert=True)`, `objects.create`, `bulk_create` и добавление через административный интерфейс отклоняются, поэтому нельзя вручную выбрать старую фиксацию, обойти архив либо связать сессию с версией другой карточки. Сохранения уже существующей сессии остаются под текущими игровыми и историческими правилами.
9. `pre_delete`-защита в `session/apps.py` расширяется на `QuizVersion`, а проверка карточки ищет сессии через все версии. `PROTECT` сохраняется на `LiveSession.quiz_version`, `current_question`, `SessionQuestionRun.question`, ссылках попыток и итогов.

Таким образом, служебное изменение черновика не может оставить ревизию 5: оно либо проходит через `save_quiz_content` и атомарно получает ревизию 6, либо отвергается без записи. Форма с прежней ревизией 5 затем получает 409 до изменения данных.

Будущие проверки этого правила:

- прямые операции `create/save/delete` для `QuizVersion`, `Question`, `Choice` и все массовые операции отклоняются, снимок строк и `content_revision` неизменны;
- одно успешное изменение нескольких вопросов/вариантов через службу повышает счётчик ровно на один, а искусственная ошибка посередине возвращает весь граф и счётчик;
- административная форма не предлагает редактирование содержимого; действия карточки используют общие службы;
- прямое `LiveSession.objects.create` отклоняется для активной, архивной, своей и чужой карточки одинаково как неподдерживаемый путь; служба создаёт только текущую зафиксированную версию неархивной карточки;
- конкурентное служебное и HTTP-сохранение с одной ревизией дают один успех и один 409.

Граница гарантии: эти меры покрывают HTTP, административный интерфейс Django, обычные `save/delete`, `QuerySet.delete/update`, `bulk_update/bulk_create` и поддерживаемые прикладные службы. Пользователь БД с правом отключать ограничения или выполнять привилегированный SQL остаётся вне доказанной гарантии. Вводить триггеры или новую схему ролей БД без отдельного требования не следует.

### 6.3. Переход данных

Бизнес-решение разрешает не переносить существующие тестовые викторины/историю, но требует сохранить пользователей, роли, хеши паролей, вход и историю миграций. Поэтому безопасная последовательность состоит из отдельной операции над данными и обычных структурных миграций.

#### Перед каждым окном развёртывания переключения

1. Остановить прикладные записи на всё время окна перехода. Это требуется как при последовательном применении подготовки и переключения в одном окне, так и при отложенном переключении после отдельно развёрнутых `quiz/0005 + session/0007`.
2. На фактически установленной версии выполнить только инвентаризацию существующей команды `stage_v_game_data --inventory` с точными базой, хостом, портом и ролью. До подготовки используется нынешний вариант команды с 12 таблицами; после части 1 — тот же расширенный вариант с `quiz_quizversion`. Команда уже проверяет фактическую цель (`stage_v_game_data.py:120-154`).
3. Подтвердить, что все целевые строки относятся к разрешённым тестовым игровым данным. При любых неожиданных данных остановиться; миграция таких данных не входит в согласованный объём.
4. Создать резервную копию, проверить её SHA-256 и восстановление в отдельной безопасной базе.
5. Выполнить `--rollback-test` с точной фразой подтверждения; убедиться, что инвентаризация полностью восстановилась.
6. Только после отдельного разрешения выполнить `--apply` с точной целью, фразой и SHA-256. Текущая команда удаляет 12 игровых таблиц, сохраняет `auth_user`, группы/связи, `django_session` и `django_migrations` (`stage_v_game_data.py:10-31,68-110,156-214`).
7. Проверить неизменность пользователей/групп, точное сохранение строк хешей паролей и успешный вход контрольной учётной записью. Сейчас тест команды подтверждает существование пользователя, но не точное значение хеша и вход (`test_stage_v_game_data_command.py:184-216`); будущая проверка должна это добавить.

Новый инструмент очистки не нужен. Для первого перехода до установки новых миграций используется команда текущей версии. Одновременно с созданием таблицы версий существующая команда получает `quiz_quizversion` в `TARGET_TABLES` между `quiz_question` и `quiz_quiz`, а её тест — отдельную строку версии. Если подготовительные миграции развёрнуты отдельно и прикладные записи возобновлялись, перед частью 2 снова используются инвентаризация, резервное копирование, проверочный откат и отдельно разрешённое применение уже расширенной команды. После переключения общая фабрика `game()` создаёт версию, поэтому в той же части адаптируется ожидание `deleted['quiz_quizversion'] > 0`. Откладывать эту поддержку до финальной документационной части нельзя.

#### Структурные миграции

Текущие последние узлы подтверждены кодом: `quiz/0004_alter_choice_options_alter_question_options_and_more` и `session/0006_stage_b_deadline_constraints`. Предлагаемый граф намеренно линейный в месте межприложенческого перехода:

```text
quiz/0004 ───────┐
                 ├─> quiz/0005_quiz_versioning_prepare
session/0006 ────┘              │
                                v
                 session/0007_quiz_versioning_prepare
                                │
                                v
                 quiz/0006_quiz_versioning_switch
                                │
                                v
                 session/0008_quiz_versioning_switch
```

| Узел | Точные зависимости | Операции и состояние после узла |
|---|---|---|
| `quiz/0005_quiz_versioning_prepare` | `quiz/0004`, `session/0006` | **Первая** операция атомарной миграции — `RunPython(require_empty_versioning_game_data, noop)`. Она читает исторические модели точной схемы `quiz/0004 + session/0006` и требует пустоты всех текущих игровых таблиц. Только после неё добавляются `Quiz.archived_at`, `Quiz.content_revision`, таблица `QuizVersion` сразу со всеми целевыми полями содержимого и необязательная `Question.quiz_version`; старые поля содержимого `Quiz` и `Question.quiz` остаются. |
| `session/0007_quiz_versioning_prepare` | `session/0006`, `quiz/0005` | Добавляется nullable `LiveSession.quiz_version`; старый `LiveSession.quiz` остаётся. После узла приложение ещё работает по прежнему договору и не создаёт версии. |
| `quiz/0006_quiz_versioning_switch` | `quiz/0005`, `session/0007` | **Первая** прямая операция атомарной миграции — `RunPython(require_empty_prepared_versioning_game_data, noop)`. Она повторно проверяет исторические модели точной подготовленной схемы `quiz/0005 + session/0007`, включая `QuizVersion`, и ничего не очищает. Только после успеха `Question.quiz_version` становится обязательным, удаляются `Question.quiz` и дублирующие поля содержимого `Quiz`, включаются ограничения порядка/состояния уже подготовленной `QuizVersion`. Код этой поставки создаёт карточку сразу с черновиком. |
| `session/0008_quiz_versioning_switch` | `session/0007`, `quiz/0006` | `LiveSession.quiz_version` становится обязательным, старый `LiveSession.quiz` удаляется. Последняя прямая операция — `RunPython(noop, prevent_versioning_reverse_with_data)`, поэтому при обратном ходе предохранитель выполняется первым и запрещает потерю любых новых карточек, версий или сессий. |

Первоначальная проверка пустоты стоит до `CreateModel`/`AddField` в `quiz/0005` и выполняется в транзакционной миграции PostgreSQL. При найденных данных не появляется таблица версий, новые столбцы и запись `django_migrations`; данные и старая схема остаются целыми. Она защищает вход в подготовку, но не считается доказательством пустоты для более позднего переключения.

Повторная проверка — первая прямая операция `quiz/0006`, до любого `AlterField`, `RemoveField`, переноса обязательности или нового ограничения. Через переданный `apps` она проверяет все исторические модели, соответствующие 13 целевым игровым таблицам расширенной команды: девять моделей `session` (`FinalAnswer`, `AnswerAttempt`, `LegacyParticipantAnswer`, `SessionCommand`, `SessionDisplayAccess`, `SessionQuestionRun`, `SessionParticipant`, `LiveSession`, `Participant`) и четыре модели `quiz` (`Choice`, `Question`, `QuizVersion`, `Quiz`). Список фиксируется в самой миграции и не импортируется из изменяемого прикладного модуля команды. Любая найденная строка вызывает адресный `RuntimeError` с указанием категорий непустых данных; миграция не изменяет и не удаляет строки. Поскольку отказ происходит первой операцией, подготовительные `0005/0007` остаются применёнными, а `quiz/0006` и зависящая от неё `session/0008` не получают записей в `django_migrations`. Автозапуск приложения и миграции никогда не вызывают очистку.

После подготовительных `0005/0007` работоспособен прежний договор: сервер сохраняет старую `Quiz` без `content_revision`, текущий клиент отправляет прежнее тело, `LiveSession` использует старый `quiz_id`, защита А не ослаблена, а обычный код не создаёт `QuizVersion`. Прикладные записи, возобновлённые между частями, могут снова наполнить старые игровые таблицы; именно поэтому окно части 2 повторно начинается с остановки записей и операционной проверки, а `quiz/0006` независимо подтверждает пустоту непосредственно перед разрушительным переключением. Семантическое переключение `0006/0008`, службы версий и совместимый клиент поставляются вместе; промежуточная эксплуатация, где сервер уже требует ревизию, а клиент её не отправляет, не допускается.

Старые файлы миграций не переписываются и не удаляются.

#### План миграционных проверок

Текущий `MigrationTransitionTests` действительно использует динамические последние узлы и всегда возвращает схему к ним в `finally` (`backend/apps/session/tests/test_migrations.py:7-148`). После добавления отказа при игровых данных исторические границы нужно сделать явными.

1. Добавить помощник, который заменяет листья только указанных приложений, например `targets_at(quiz='0004_...', session='0004_...')`, сохраняя текущие листья остальных приложений. Нельзя определять границу А или Б словом `latest`.
2. `test_old_schema_requires_explicit_preparation_and_preserves_accounts` оставить проверкой перехода с `quiz/0002 + session/0002` только до границы А `quiz/0004 + session/0004`. Ожидаемый отказ `quiz/0003` и последующий разрешённый проход после явной очистки синтетических игровых строк сохраняются; пользователь, хеш и вход проверяются на этой границе.
3. `test_stage_b_migration_preserves_legacy_history_and_marks_safe_sessions` и `test_stage_b_migration_stops_on_active_legacy_question` выполнять от границы А `quiz/0004 + session/0004` только до границы Б `quiz/0004 + session/0006`. Так сохраняется собственный смысл классификации `session/0005`, не смешанный с новым требованием пустоты всей истории.
4. Добавить отдельный тест чистой установки: снять только миграции приложений `quiz/session` до `None` в пустой транзакционной тестовой базе, затем пройти до текущих листьев и проверить наличие целевой схемы/ограничений. В `finally` восстановить текущие листья.
5. Добавить тест подготовленного обновления без новых записей: перейти на точную базу `quiz/0004 + session/0006`, оставить пользователя/группы/хеш, но не игровые строки, затем пройти `0005 → 0007 → 0006 → 0008`; проверить обе проверки пустоты, целевую схему, неизменные учётные данные и вход.
6. Добавить тест отказа: на `quiz/0004 + session/0006` создать синтетическую карточку/сессию, попытаться пройти в `quiz/0005`, ожидать точный `RuntimeError`, после чего проверить сохранность строк, отсутствие `quiz_quizversion` и новых столбцов, а также отсутствие `quiz/0005` в `django_migrations`.
7. После ожидаемой ошибки тест остаётся на старой схеме. В `finally` он через исторические модели явно удаляет только созданные им синтетические строки в порядке зависимостей, пересоздаёт `MigrationExecutor` и проходит до текущих листьев. Это видимая уборка тестовой фикстуры, а не скрытое удаление в миграции или ослабление предохранителя.
8. Добавить параметризованную проверку промежуточного состояния. Сначала применить только `quiz/0005 + session/0007` и сохранить их записи и времена применения из `django_migrations`. Через исторические модели этой подготовленной схемы создать только собственные синтетические данные: один вариант проверяет старый граф `Quiz/Question/Choice` и при необходимости сессию, другой — строку новой `QuizVersion`. Попытка пройти `quiz/0006 + session/0008` должна получить адресный `RuntimeError` от первой операции `quiz/0006`. После отказа проверяются неизменность всех синтетических строк, наличие старых полей `Quiz` и связей `Question.quiz`/`LiveSession.quiz`, сохранность новых необязательных связей подготовительной схемы, неизменные записи `0005/0007` и отсутствие записей `0006/0008` в `django_migrations`.
9. В продолжении того же сценария через те же исторические модели явно удалить только созданные тестом строки в порядке зависимостей, пересоздать `MigrationExecutor` и снова запросить `quiz/0006 + session/0008`. Переход должен завершиться успешно; записи и времена применения `0005/0007` остаются прежними, а в `django_migrations` добавляются `0006/0008`. Это доказывает успешный повтор без отката и повторного исполнения подготовки; автоматическая или скрытая очистка миграцией не используется.
10. Добавить две обратные проверки: пустая целевая схема допускает структурный откат до `quiz/0004 + session/0006` и повторное применение; наличие любой новой карточки/версии/сессии вызывает `prevent_versioning_reverse_with_data` до первого удаления столбца и оставляет схему/данные неизменными.

#### Восстановление

- До `--apply`: никаких данных не изменено.
- После неуспешного `--rollback-test`: транзакция обязана вернуть прежнюю инвентаризацию; иначе переход прекращается.
- После очистки, но до успешного развёртывания: откатить приложение на прежний коммит и восстановить проверенную резервную копию; повторный запуск без выяснения причины запрещён.
- Если проверочная миграция остановилась из-за строк, её транзакция не удаляет данные. Следующий шаг — новая инвентаризация, а не ручное удаление из миграции.
- Структурный обратный ход миграций допустим только при остановленном приложении и полностью пустых новых игровых таблицах; это проверяется предохранителем и отдельным тестом.
- После появления новой карточки, черновика или исторической сессии обратные `0008 → 0004/0006` недопустимы, поскольку они уничтожили бы новое содержимое. Исправление схемы выполняется новой прямой миграцией. Полное возвращение к старому выпуску возможно только восстановлением заранее проверенной резервной копии с явным признанием потери всех данных после её момента.

Дополнительные обязательные регрессии:

- `description`, оба флага показа и оба общих времени входят в каноническое сравнение и версию. Текущий `quiz_data` содержит не все эти поля (`backend/apps/quiz/validation.py:33-37`), поэтому для сравнения нужен полный единый построитель содержимого.
- ID варианта другого вопроса, ID вопроса другой версии/карточки и повтор одного ID в теле отклоняются без частичной записи.
- Архивная карточка не сохраняется и не запускается, но читается в архиве и через свою старую историю.

## 9. Утверждённое решение по предпросмотру

### Решение от 6 сентября 2026 года

Пользователь утвердил вариант А. Предпросмотр открывается из конструктора, читает текущие значения редактора, включая несохранённые правки, ничего исторического не создаёт и возвращает к тем же данным редактирования.

**Статус варианта А: утверждено, реализовано и принято оркестратором в части 4; замечания Б4-4-01–Б4-4-02 закрыты.** Перед открытием выполняется та же локальная валидация, что используется перед сохранением. Если обязательные поля или варианты неполны либо некорректны, предпросмотр не открывается, ошибки показываются у формы, весь ввод сохраняется. Автосохранения и HTTP нет.

Последствия: пользователь видит именно то, что редактирует; нет скрытых записей и нового API; режим точно отделён от тестовой сессии. Цена — потребуется чистый клиентский виджет предпросмотра и тест совпадения его правил с игровыми экранами.

Отклонённый вариант Б предполагал показ только последнего успешно сохранённого серверного содержимого.

Последствия: реализация может читать существующий GET, но предпросмотр часто будет отставать от видимой формы; понадобится явное предупреждение или принудительное сохранение. Принудительное сохранение перед просмотром противоречит ожидаемой безопасной границе и может дать 409, поэтому этот вариант хуже.

Повторное согласование семантики предпросмотра не требуется. Нерешённых бизнес-вопросов анализ не выявил. Следующее решение по части 4 — только её приёмка и отдельное разрешение коммита. Обнаружение нетестовых игровых данных на будущей инвентаризации является стоп-условием перехода, а не поводом заранее расширять объём миграции.
