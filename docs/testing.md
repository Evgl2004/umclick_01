# Проверки umclick

Исполнителям не требуется самостоятельно искать команды запуска. Все проверки выполняются из корня проекта через три сценария в `scripts/`.

## Серверная часть

Один раз создайте `.env.test.local` по примеру `.env.test.example` и заполните пять параметров локального PostgreSQL. Файл исключён из Git; пароль нельзя передавать в сообщения, команды или документацию.

```powershell
.\scripts\check-backend.ps1
.\scripts\check-backend.ps1 -Coverage
```

Сценарий проверяет конфигурацию Django, отсутствие забытых миграций, безопасность подключения и полный набор серверных тестов. Применяются `umclick.test_settings` и постоянная выделенная база PostgreSQL с именем из `UMCLICK_TEST_DB_NAME`; SQLite не используется. Основное и тестовое имена базы совпадают, обе ветки тестов используют `--keepdb`, поэтому существующая база сохраняется после запуска.

Тестовая роль должна быть владельцем этой базы и не иметь прав `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION` и `BYPASSRLS`. Ей разрешается подключаться только к выделенной тестовой базе. Перед тестами сценарий проверяет фактические базу, роль, владельца и административные права. База должна существовать заранее: сценарий не создаёт, не переименовывает и не удаляет базы.

Запускайте только один экземпляр серверных проверок одновременно. Параллельный запуск и клонирование баз не используются. Миграции и тесты изменяют схему и данные внутри выделенной тестовой базы, поэтому в ней не должно быть пользовательских или рабочих данных.

На этом компьютере системный Python и `.venv\Scripts\python.exe` недоступны. Поэтому сценарий использует Python из pgAdmin и подключает установленные пакеты из `backend\.venv\Lib\site-packages`. Расширенный доступ, контейнеры и отдельная подготовительная команда не требуются.

Покрытие сохраняется в `backend/.coverage`, HTML-отчёт — в `backend/htmlcov`.

### Конкурентная корректность этапа Б

Штатный серверный прогон включает статическую проверку параметризованного SQL, границ транзакций и порядка блокировок, а также проверки на настоящем PostgreSQL с отдельными соединениями и управляемыми барьерами. Проверяются:

- параллельные ответы разных участников и последовательные ответы одного участия;
- обе очередности ответа и финализатора по ВОП-02;
- атомарный откат без частичных итогов;
- идемпотентность команд и попыток, один итог и неизменяемость результата;
- 21 конкурентная уникальная попытка с доказанным пределом 20 строк;
- область `FOR SHARE` только для доверенного текущего запуска и план SQL-запроса;
- отсутствие исключительной блокировки при раннем восстановительном чтении и один переход при двух конкурентных проверках наступившего срока;
- ролевую область события попытки и сохранение фазовых получателей;
- числовые и `null`-типы фактически отрисованного JSON 409;
- неизменность закрытых агрегатов после поздней аудиторской попытки;
- изоляцию сбоя одной ролевой отправки без ложной ошибки успешной операции.

Проверка плана не задаёт нормативов задержки или пропускной способности. Полное соответствие БП-01–БП-16 зафиксировано в [акте передачи этапа Б](block-1-stage-b-handoff.md). Отдельные многопроцессные и ограниченные нагрузочные проверки этапа В описаны ниже; они также не устанавливают SLO.

### Redis и несколько ASGI-процессов этапа В

Обычный `check-backend.ps1` не требует внешнего Redis и явно пропускает две интеграционные проверки. Для их запуска нужен уже работающий Redis на loopback; сценарий не устанавливает, не запускает и не перенастраивает службу. Каждый прогон обязан использовать новое пространство `umclick:test:<UUID>`:

```powershell
$runId = [guid]::NewGuid().ToString()
$python = 'C:\Program Files\PostgreSQL\17\pgAdmin 4\python\python.exe'
$env:UMCLICK_RUN_REDIS_INTEGRATION = 'true'
$env:UMCLICK_STAGE_V_REDIS_URL = 'redis://127.0.0.1:6379/0'
$env:UMCLICK_STAGE_V_REDIS_NAMESPACE = "umclick:test:$runId"
try {
    $ping = "import sys; sys.path.insert(0, r'backend/.venv/Lib/site-packages'); import redis; ok=redis.Redis.from_url('redis://127.0.0.1:6379/0', socket_timeout=1).ping(); print('PONG' if ok else 'NO_PONG'); raise SystemExit(0 if ok else 1)"
    & $python -B -X utf8 -c $ping
    if ($LASTEXITCODE -ne 0) { throw 'Python-клиент Redis не получил PONG.' }
    .\scripts\check-backend.ps1
}
finally {
    $cleanup = "import sys; sys.path.insert(0, r'backend/.venv/Lib/site-packages'); import redis; c=redis.Redis.from_url('redis://127.0.0.1:6379/0', socket_timeout=1); p=sys.argv[1]+':*'; k=list(c.scan_iter(match=p)); c.delete(*k) if k else None; print('OWN_KEYS_AFTER=' + str(sum(1 for _ in c.scan_iter(match=p)))); c.close()"
    & $python -B -X utf8 -c $cleanup $env:UMCLICK_STAGE_V_REDIS_NAMESPACE
    Remove-Item Env:UMCLICK_RUN_REDIS_INTEGRATION -ErrorAction SilentlyContinue
    Remove-Item Env:UMCLICK_STAGE_V_REDIS_URL -ErrorAction SilentlyContinue
    Remove-Item Env:UMCLICK_STAGE_V_REDIS_NAMESPACE -ErrorAction SilentlyContinue
}
```

Тест выполняет производственный Lua через настоящий Redis, включая детерминированную границу 40/41, пополнение, WebSocket-пределы и освобождение аренды. `tearDown()` удаляет вычисленные ключи адресных тестов, а внешний `finally` удаляет остальные технические Channels-ключи только того же уникального пространства. Итог обязан вывести `OWN_KEYS_AFTER=0`; `FLUSHALL` и `FLUSHDB` запрещены.

Минимальная двухпроцессная проверка без контейнеров:

```powershell
& 'C:\Program Files\PostgreSQL\17\pgAdmin 4\python\python.exe' -B -X utf8 scripts\check-stage-v-multiprocess.py
```

Оба Daphne-процесса получают `DJANGO_SETTINGS_MODULE=umclick.test_settings`, проверяют фактические `current_database()` и роль, подключаются к одной выделенной `test_umclick_*` и одному уникальному Redis-пространству. `InMemoryChannelLayer` отклоняется. В `finally` завершаются все запущенные процессы, освобождаются порты и удаляются только собственные ключи. Ошибочный путь остановки отдельно проверяется параметром `--fail-after-first`; ненулевой код в нём ожидаем и должен проверяться внешней оболочкой.

Ограниченная нагрузочная проверка:

```powershell
& 'C:\Program Files\PostgreSQL\17\pgAdmin 4\python\python.exe' -B -X utf8 scripts\check-stage-v-load.py
```

Сценарий не принимает внешний адрес, сам запускает один Daphne только на `127.0.0.1`, требует `test_umclick_*`, использует 30 участников и до 20 попыток каждого — всего 600 на один вопрос. Он публикует одну JSON-строку с количеством успехов/ошибок, p50/p95/p99/max, общей длительностью и фактической частотой ответов. Норматив производительности не задан. После прогона адресно удаляются только созданный граф тестовой базы и собственные ключи Redis; порт должен повторно захватываться.

Граница `try/finally` устанавливается до первой мутации базы. Два управляемых ошибочных пути отдельно доказывают очистку частичного графа после создания пользователя и после создания викторины; оба запуска обязаны вернуть ненулевой код и нулевые собственные строки/ключи. Loopback-порт на этих ранних шагах ещё не выделяется, поэтому ожидается `ports_released: 0`:

```powershell
& 'C:\Program Files\PostgreSQL\17\pgAdmin 4\python\python.exe' -B -X utf8 scripts\check-stage-v-load.py --fail-after-user
& 'C:\Program Files\PostgreSQL\17\pgAdmin 4\python\python.exe' -B -X utf8 scripts\check-stage-v-load.py --fail-after-quiz
```

Эти сценарии не проверяют Nginx, мобильную вёрстку, публичный стенд, ресурсы хоста или внешний запрет прямого доступа к backend. Такие пункты нельзя помечать успешными по результату loopback-прогона.

### Версии викторин и переключение схемы

Штатный серверный набор проверяет создание карточки с черновиком, сохранение по `content_revision`, холостой повтор без записей, изменение черновика на месте, новые дочерние идентификаторы после фиксации, повторное использование равной фиксированной версии, неизменность истории и атомарный откат фиксации при отказе создания сессии. В `QuizVersioningServiceTests` адресно проверяются:

- `test_partial_save_normalizes_new_items_and_preserves_existing_fields` — значения по умолчанию нового вопроса и варианта, сохранение отсутствующих полей существующих элементов и повтор без изменений;
- `test_invalid_partial_content_does_not_change_graph_or_revision` — содержательная ошибка до записи;
- `test_role_checks_are_identical_for_supported_services` — запись без роли, отозванная роль владельца, чужой преподаватель, владелец и администратор;
- `test_save_rolls_back_partial_draft_update_and_allows_retry` и `test_save_rolls_back_new_draft_graph_and_allows_retry` — откат после уже выполненной части дочерних записей и успешный повтор для обеих ветвей сохранения;
- `test_history_answers_results_and_csv_keep_fixed_content_after_full_edit` — сохранность фиксированных вопросов, вариантов, настроек, попыток, итогов, рейтинга и CSV после полной правки карточки;
- `test_select_count_does_not_grow_with_children_or_history` — отсутствие дополнительных `SELECT` при росте числа вопросов, вариантов и исторических версий.

`QuizVersioningApiTests` закрепляет точный ответ 409 с `current_content_revision`, нормализацию частичного HTTP-запроса, атомарный отказ ошибочного содержимого и постоянное число `SELECT` списка при росте истории. Отдельные соединения PostgreSQL с управляемыми барьерами в `PostgreSQLConcurrencyTests` подтверждают, что из двух сохранений одной редакции проходит только одно, сохранение с созданием сессии упорядочены блокировкой стабильной `Quiz`, удаление и создание сессии безопасны в обеих очередностях, два запуска одной карточки используют одну фиксацию, а реальная конкурентная коллизия PIN разрешается повторной генерацией после пересечения транзакций.

`MigrationTransitionTests` проходит точные границы `quiz/0005 + session/0007` и `quiz/0006 + session/0008`. Он создаёт собственные данные в подготовленной схеме, ожидает отказ первой операции `quiz/0006`, проверяет сохранность данных, старых полей, записей и точного времени применения подготовительных миграций, затем успешно повторяет переход после адресного удаления фикстуры. `test_switch_guard_checks_quiz_version_independently` отдельно вызывает прямую операцию с историческим реестром моделей: сначала сверяет все 13 обращений, затем делает непустой только `QuizVersion` и подтверждает адресный отказ. Пустой обратный ход и отказ обратного хода при новых данных проверяются отдельно. Эти тесты используют только выделенную тестовую PostgreSQL; миграции не очищают данные автоматически.

Клиентские тесты проверяют сохранение дочерних идентификаторов и `content_revision` в преобразователе, их возврат в тело сохранения и локализованное объяснение `quiz_revision_conflict`. Два виджет-теста `teacher_panel_save_test.dart` работают с настоящим `TeacherPanel`: первый доказывает, что успешный ответ `PUT` остаётся состоянием редактора при последующем отказе списка и следующая отправка использует новые идентификаторы и редакцию; второй сохраняет всё несохранённое состояние после 409, не переносит `current_content_revision` из ошибки и не запускает автоматический повтор или обновление списка.

Для Б4-2-07 чистая проверка `следующий вопрос определяется только снимком викторины сессии` в `form_interaction_test.dart` подтверждает порядок и безопасный отказ при неизвестном снимке. Виджет-тест `снимок сессии управляет переходом после обновлений списка и состояния` в `teacher_panel_save_test.dart` проходит настоящий `TeacherPanel`: зафиксированные вопросы 11/12 сохраняют доступный переход с вопроса 11 при черновике 101/102, обновлённом, пустом и недоступном списке; очередное WebSocket-состояние не теряет снимок, а вопрос 12 отключает переход. Сам `TeacherLiveSessionCard` дополнительно сохраняет прежние ограничения статуса и фазы.

### Архивирование и безопасное удаление

`QuizArchiveApiTests` проверяет договор критериев 7–11:

- `test_open_session_of_non_latest_version_blocks_archive_exactly` — обе открытые стадии любой, в том числе не последней, версии дают точный `409 quiz_open_session_conflict` и не меняют карточку, версии или связь сессии;
- `test_terminal_sessions_allow_idempotent_archive_restore_and_new_work` — завершённая и остановленная сессии не мешают, повторы архива и восстановления не меняют `content_revision`, даты повторно и состав версий, архив запрещает сохранение/запуск, а восстановление снова разрешает их;
- `test_lists_detail_permissions_and_can_delete_contract` — раздельные рабочий и архивный списки, чтение архивной карточки, строгий фильтр, права владельца/администратора и запрет чужого доступа;
- `test_delete_unused_cascades_and_used_card_is_fully_preserved` — каскад только неиспользованного графа и точный `409 quiz_history_protected` для владельца и администратора без частичного изменения истории;
- `test_can_delete_uses_one_exists_annotation_for_the_whole_list` — серверная подсказка вычисляется одним `EXISTS`, а число чтений списка не растёт от числа использованных карточек;
- `test_archive_and_restore_leave_answers_ranking_and_csv_unchanged` — для `finished` и `aborted` свежие снимки версии, вопросов, вариантов, сессии, участия, попыток и итогов, а также успешные detail/list/ranking/CSV сравниваются до архива, непосредственно в архиве и после восстановления.

`QuizArchiveProtectionAndAdminTests` подтверждает запрет прямой и массовой записи `archived_at`, использование тех же служб административными действиями и общий откат группового действия при одной защищённой карточке. В `PostgreSQLConcurrencyTests` управляемые барьеры проходят обе существенные очередности архива/создания сессии, архива/сохранения, удаления/создания сессии и архива/завершения; завершение не меняет принятого игрового порядка блокировок. Дополнительные HTTP-регрессии удаляют карточку после предварительного чтения, фиксируют 404 для архива, восстановления, удаления, сохранения и создания сессии, проводят ожидающую операцию через зафиксированное удаление и подтверждают, что конкурентное удаление ждёт материализации успешного ответа archive/restore.

Клиентские регрессии проверяют точные методы, пути, фильтр и пустые тела `ApiClient`, локализацию трёх кодов конфликта и настоящую панель преподавателя. Новые описания части 3 локализованы: «конфликт архива сохраняет выбранную карточку и форму без обновления», «архивирование и восстановление обновляют списки и сохраняют режим чтения», «безвозвратное удаление зависит от can_delete и требует подтверждения». Отдельные сценарии с рабочей А и архивной Б доказывают, что загруженная Б не разблокируется рабочей вкладкой, рабочая несохранённая форма переживает переход туда и обратно, восстановленная Б снова редактируется только после рабочей загрузки, а отказ другого списка сохраняет форму и согласованный режим.

### Локальный предпросмотр викторины

Файл `test/features/teacher/quiz_preview_test.dart` проверяет часть 4 на настоящем `TeacherPanel` с контролируемым HTTP-клиентом и отдельно на чистом представлении:

- `новая валидная форма открывает локальный предпросмотр без POST` — новая форма нормализуется, необязательные пустые варианты не показываются, а открытие и закрытие не добавляют ни одного запроса;
- `невалидная форма не открывается и сохраняет введённые данные` — используется та же локализованная ошибка, что перед сохранением, а контроллеры и журнал HTTP остаются неизменными;
- `длинное русское описание не перекрывает управление и сохраняется после закрытия` — настоящая панель при 1280×720 проходит 40 строк описания, переключение вопроса, экрана и состояния, закрытие и проверку исходного текста формы без переполнения;
- `несохранённые изменения переживают цикл предпросмотра и обычный PUT` — два открытия читают очередные несохранённые значения, переключения и закрытия не обращаются к сети, а последующий обычный `PUT` сохраняет название, описание, настройки, вопросы, варианты, правильность, дочерние идентификаторы и исходный `content_revision`;
- `чистый предпросмотр соблюдает экраны состояния и позднее раскрытие` — вручную проходят оба вида экрана, три состояния и два вопроса; правильность отсутствует до результата и исчезает после обратного перехода;
- `все сочетания видимости следуют договору экрана участника` — отдельные заранее заданные ожидания проверяют `true/false`, `false/true`, `true/true` и `false/false`, не повторяя вычисление виджета;
- `шесть вариантов меняют обозначения вместе с выбранным экраном` — пятый и шестой варианты используют фиолетовую звезду и бирюзовый шестиугольник на экране аудитории, а на экране участника повторяют его четырёхпозиционные обозначения; правильность раскрывается и снова скрывается;
- `узкое русское окно сохраняет доступ к управлению` — при 390×720 нет ошибок компоновки, горизонтальная прокрутка оставляет доступными выбор второго вопроса, экрана участника и состояния ответа.

Эти проверки доказывают отсутствие клиентских HTTP-вызовов после исходной загрузки панели. Отсутствие серверных записей следует из архитектурной границы: `QuizPreviewDialog` не имеет зависимостей от API, WebSocket и игровых страниц; сервер и база в части 4 не запускаются.

## Клиентская часть

```powershell
.\scripts\check-frontend.ps1
.\scripts\check-frontend.ps1 -SkipBuild
```

Сценарий последовательно выполняет получение зависимостей по `pubspec.lock`, проверку форматирования без изменения файлов, статический анализ, тесты и web-сборку. Параметр `-SkipBuild` пропускает только сборку.

Сценарий использует штатные команды установленного Flutter. Если изолированная среда исполнителя запрещает Flutter записать служебный файл внутри каталога SDK (например, `flutter\bin\cache\libimobiledevice.stamp`), не создавайте обходной контур и не изменяйте SDK. Выполните ту же команду `.\scripts\check-frontend.ps1` в обычном PowerShell и передайте исполнителю полный результат.

## Полная проверка

```powershell
.\scripts\check-all.ps1
.\scripts\check-all.ps1 -Coverage
.\scripts\check-all.ps1 -SkipFrontendBuild
```

Сначала выполняется серверная часть. При её ошибке клиентская часть не запускается.

Сценарии не устанавливают Python, Flutter или PostgreSQL, не запускают службы, не обращаются к стенду и не очищают пользовательские данные.
